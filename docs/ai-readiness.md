# AI integration readiness checkpoint

The following describes the readiness checkpoint. The subsequent
[OpenAI integration](openai-planner.md) adds a configurable worker provider,
renewable leases, durable proposal reuse, and an explicit live evaluator.
Deterministic generation remains the default.

This checkpoint prepares generation semantics and execution safety. It makes no
model calls, adds no prompts or credentials, and does not select a model. The
deterministic generator remains the production provider.

## Hard constraints

New proposals must satisfy workout schemas, positive durations, exact duration/block
accounting, valid sport/target combinations, resolvable targets, date/replacement
windows, and unique IDs. Missing numeric baselines require another supported target
such as RPE. Provider-supplied resolved values and effort labels are recomputed.

Explicit unavailable days, permitted sports, pool access, shared daily minutes,
daily session counts, NO_TRAINING and MAX_SESSION_MINUTES restrictions remain binding.
The existing zero-goal meaning remains: no new workouts for that sport. Positive
goals and adjusted volumes are targets, not upper bounds. CONTEXT_ONLY restrictions
remain information for interpretation rather than executable prohibitions.

The server selects protected workouts from owned saved plans. Past, completed,
modified, stopped, and locked workouts remain unchanged; a proposal cannot replace
their IDs. Retained workouts count against daily capacity. If retained history
already exceeds a new restriction, it is retained rather than rewritten.

HTTP session/origin checks and database ownership scoping remain authoritative.
Request ownership, freshness, lease/attempt ownership, and newer requests are checked
before saving. Invalid proposals or failed writes leave the existing plan intact.

## Soft deviations and goal semantics

`FlexiblePlan.analysis` contains computed measurements, not validation errors:

| Type | Evidence |
| --- | --- |
| VOLUME_INCREASE / VOLUME_DECREASE | Proposed minutes, previous completed week, established comparison, percentage changes, established sample count |
| SESSION_FREQUENCY_INCREASE | Proposed sessions versus previous recorded week |
| LONG_SESSION_INCREASE | Proposed longest session, previous-week longest, longest in the recorded window |
| INTENSITY_INCREASE | More proposed hard sessions than completed plan hard targets last week, where such observations exist |
| HARD_SESSION_CLUSTER | Hard-session pairs on adjacent calendar dates |
| SAME_DAY_HARD_SESSIONS | Hard-session count and pair count on the same date |
| GOAL_DIFFERENCE | Saved goal, adjusted target, proposed minutes, signed difference |
| NO_REST_DAY | All seven dates contain training |

All nonzero recorded-volume differences are measured; there is no arbitrary
10-percent rejection threshold. The total number of hard sessions, counts per
sport, same-day pairs and adjacent-day pairs are also stored. Pair counts include
cross-sport sessions. Exact recovery hours are null because scheduling is by date.

235 or 250 bike minutes can both be accepted for a 240-minute goal. Goals remain
unchanged. The UI shows goal/planned totals and explains differences in either
direction. No new deviation dashboard was added; structured analysis is stored in
the plan and is available to consumers/evaluation tooling.

The deterministic fallback still prefers a rest day, at most two hard sessions,
and no adjacent hard dates, and fills adjusted targets in five-minute increments.
These are its scheduling choices, not requirements imposed on future providers.
The default-availability 120-run/240-bike/0-swim case still produces 360 minutes.

## Recorded history

`PlanningContext.trainingHistory` adds twelve completed local calendar weeks while
preserving the existing three-week automatic goal calculation. It reuses the numeric
training summary logic. Each sport/week includes recorded minutes, session count,
longest session, and counts of completed plan sessions/hard targets.

The established-volume comparison is the median of the three highest nonzero
recorded weekly volumes within this window. With fewer than three, the sample count
makes sparse evidence explicit. No recorded volume means a null established value.
Percentage changes from zero are null, never infinity. This is a descriptive
comparison, not an assertion that the athlete tolerated the volume or can safely
return to it. The full twelve-week sequence is included so a future provider can
use its own interpretation rather than rely on the comparison alone.

Recorded activity does not prove completion quality. Empty weeks may indicate
missing sync data. Activity streams are not used to infer intensity. Completed plan
targets are a partial proxy and are kept separate from activity counts. Intensity
increase is not inferred from absent evidence. Existing feedback remains available.

History and saved analysis are optional additive schema fields so old v1/v2 plans
and older context fixtures remain readable. Fresh DB-built contexts include history.

## Snapshot, generation, and guarded save

1. Create/reuse the owned persistent request with a fixed target week. BullMQ still
   carries only `{ jobRunId }`. Sync and active queued generation remain exclusive.
2. Claim an attempt with its existing lease. Under a short per-athlete training lock,
   load the planning input and protected workouts. Persist that snapshot in the
   existing `JobRun.planRequest` JSON. No migration is required.
3. Release the transaction before calling the asynchronous provider. Each correction
   sees a separate copy of the same validated snapshot.
4. Reacquire the training lock. Verify RUNNING status, attempt number, unexpired
   lease, request ownership, and absence of a newer request. Rebuild input at the
   original snapshot time and compare it structurally to the frozen input. A local
   date rollover also invalidates the result.
5. If inputs differ, cancel this request and keep the existing plan. If unchanged,
   save the plan and SUCCESS status in one transaction.

A new request after an input edit supersedes an active matching request whose
snapshot is stale. A late A cannot write over B: its status/attempt and the newer
request check fence it out. Duplicate successful deliveries return SUCCESS without
calling the provider. Infrastructure recovery reuses the persisted snapshot; it
does not silently replan from different inputs.

Freshness compares relevant domain values, including saved-plan versions and
feedback; it is not a new global revision counter. An edit reverted to exactly the
same inputs need not invalidate the result. Writes through supported settings,
goal, race, evidence and feedback functions coordinate using the same training lock.
Future mutation paths must follow that rule. Direct external SQL is outside this
application-level concurrency protocol.

The direct DB generation helper also generates outside its transaction and checks
input freshness before saving. The web production path continues to use BullMQ.

## Proposal correction versus infrastructure retry

`PlanProvider(input, { attempt, previousErrors })` supports asynchronous results.
`generatePlanWithCorrections` allows three proposal attempts. Failures expose
`code`, `path`, `message`, and where applicable `workoutId`. Codes distinguish
schema, date, protection/duplicate ID, availability/restriction, daily capacity,
excluded sport, unresolved target, and final plan-structure errors.

Three invalid proposals cause a terminal failure; BullMQ does not multiply that
correction loop. Provider/network exceptions escape to the infrastructure layer,
which uses the existing persistent attempt limit/backoff. A transport failure may
cause a later execution to invoke the provider again with the same snapshot, so
three proposal attempts are not a guarantee of only three billable network calls across
all infrastructure failures. No real provider transport/retry policy is added here.

The existing lease lasts two minutes. Results after lease expiry cannot commit.
Before a real provider is connected, choose request timeouts/cancellation and, if
needed, lease renewal. A slow call may continue computing after being superseded,
but its result cannot save. This checkpoint addresses correctness, not cancellation
of an external service that is not connected yet.

## Evaluation fixtures

`tests/fixtures/planning-scenarios.mjs` exports fresh validated generation inputs for:

1. Normal 70.3 build.
2. Equally important 70.3 and two-minute cycling event.
3. Low-priority secondary event.
4. Return after illness with higher recorded prior volume.
5. Return after travel.
6. Restricted weekdays.
7. Adjacent available days that can force hard sessions together.
8. Same-day hard-session opportunity with unknown recovery hours.
9. No pool.
10. No FTP, with running HR/RPE available.
11. Large temporary volume reduction.
12. Large temporary increase.
13. Locked workout in remaining-week generation.
14. Completed workout in remaining-week generation.
15. Run restriction, bike/swim allowed.
16. Different race dates.
17. Sparse lower-volume history.
18. Coherent 235/250-minute bike plan versus a 240-minute target.

These are inspectable cases, not exact-plan assertions or a coaching-quality score.
Tests separately submit clustered hard workouts and off-goal durations, so permissive
semantics are verified even though the fallback does not choose those patterns.

Run `npm run evaluate:planner` to print deterministic results as JSON. Import
`evaluatePlanner(provider)` from `scripts/evaluate-planner.mjs` to reuse these inputs
with another implementation later. No credentials or database are needed for this runner.

## Validation results

All 147 tests passed: semantics 20, adaptive planner 21, planner 27, planning context
10, OAuth 13, sync 28, training summaries 9, settings 7, calendar 5, health 3,
and Ping route 4. The evaluation runner also passed all 18 synthetic scenarios.

Integration suites used disposable databases and isolated queue prefixes.

Commands: `npm run typecheck`, `npm run lint`, `npm run build`,
`node scripts/test-strava.mjs <suite>` for the suites above, and
`npm run test:ping-route`. `npm run test:semantics` runs the new checkpoint suite.
