# Planning settings UI — September 6, 2026

This increment exposes the existing PlanningContext storage through Profile, Goals,
and Availability pages. A responsive sidebar connects them to the calendar. Settings
are persisted in Postgres for the signed-in athlete; the deterministic v1 planner
still uses its fixed UTC schedule and does not apply these new inputs yet.

## Implemented behavior

| Page | Inputs and behavior |
| --- | --- |
| `/settings/profile` | Timezone, manual cycling FTP in watts, running maximum HR in bpm, and swim threshold pace in seconds per 100 m or 100 yd. Blank baselines remove the manual override. |
| `/settings/goals` | Add, edit, and remove races with date, event type, sports, optional distance/duration/performance goal, and independent importance scores from 0 to 100. The slider and numeric input edit the same score; equal scores are allowed. A link opens the existing weekly volume goal editor on the calendar. |
| `/settings/availability` | Configure each weekday's total minutes, maximum sessions, permitted sports, and pool access. An unchecked day remains unspecified. Zero sessions/minutes represents a rest day. Date overrides replace that date's usual settings and can include a reason. |

On mobile, a Menu button opens the same navigation. Forms report save errors and
keep entered values available for retry. Successful saves update the editor from
the committed database result. Calendar workouts are not regenerated by saving settings.

## Data and API decisions

`GET /api/planning-settings` returns the authenticated user's editable settings.
`PATCH` accepts one strict, discriminated mutation: PROFILE, AVAILABILITY,
RACE_CREATE, RACE_UPDATE, or RACE_DELETE. No browser-supplied user ID is accepted.
Writes require the configured application origin and a valid session; responses
are uncached. The existing `@pkg/shared` and `@pkg/db` boundaries remain intact.

Profile edits merge manual baselines into the stored profile. Availability edits
replace only availability. Estimates, custom zones, capabilities, and restrictions
survive both operations. An unchanged baseline retains its provenance; a changed
manual value receives a new timestamp. Clearing a manual value leaves any existing
estimate available to context construction.

The swim pace unit selector converts an entered manual pace. Unit changes are
blocked when an existing estimate or custom swim zones use the old unit, avoiding
silently relabeling those values.

Transactions lock the user's row to serialize settings writes, including first
profile creation. Profile/availability and race edits compare `expectedUpdatedAt`
against the stored version. A stale edit returns 409 instead of overwriting newer
data; the user can explicitly discard unsaved edits and reload. Race writes check
ownership. Changes to an event's type, distance, duration, or sports clear its saved
demand profile; date, importance, name, and performance-goal edits preserve it.
Clients cannot submit a trusted demand profile through this endpoint.

No migrations, dependencies, services, or queue jobs were added. These small
configuration writes use the web application's existing database access pattern.

## Verification

With the existing database and Strava session available, start the app normally:

1. Open Profile, save a timezone and baseline, then reload and verify persistence.
2. Open Availability, configure a pool day and a date-specific rest override, save,
   and reload. Unconfigured days should remain unconfigured.
3. Open Goals, create two races with equal importance, edit one score, and remove
   a race. Follow the weekly volume goals link to the calendar's existing editor.
4. Open the same profile in two tabs. Save in the first tab, then try saving in
   the older tab. Expect a conflict with an explicit discard-and-reload option.
5. At mobile width, use Menu to navigate. Calendar workouts should remain intact.

Validation completed for this increment:

- All workspace typechecks, web lint, and full production build passed.
- Seven settings tests, ten PlanningContext regressions, and 27 deterministic
  planner regressions passed: 44 integration tests in total.
- Headless Chrome with isolated fixtures verified profile/availability persistence,
  race creation/editing/deletion, the weekly goals link, failed-save retry,
  mobile navigation/overflow, unauthenticated rendering, and no browser page errors.
- Desktop and mobile screenshots were inspected. Tests did not change live user
  data or issue real Strava requests.

## Next boundary

The settings are available to `buildPlanningContext`, but generation must explicitly
consume and enforce them in a later increment. Running pace/custom zone editors,
restriction editing, automatic fitness updates, feedback-driven adaptation, and
AI workout generation remain unimplemented. The UI states this limitation so
saving pool access or changing a race is not mistaken for changing the calendar.
